# build45 검증 범위

build44의 같은 세션 `4603f3b3-a4d2-4746-8a10-03cf949d867e`에서 Windows는 6,464프레임을 인코딩하고 3,270프레임만 데이터 채널에 투입했다. 3,193프레임이 송신 측에서 버려졌고, iPad는 3,188개를 완성했다. iPad 표시 계층 드롭은 0이었으나 진단 직전 최근 완료 FPS가 0이었다. 이것은 수신 표시 계층보다 송신 큐와 전송 경로를 먼저 다뤄야 함을 뜻한다.

## 변경과 검증

- 1080p60은 12Mbps에서 시작하며 18Mbps 순간 상한을 둔다. 큐가 1MiB 이상이거나 초당 드롭이 반복되는 상태가 5회 이상 관측되고 직전 조정 후 10초 이상 지났을 때 목표를 65%로 낮춘다. 최저 4Mbps.
- 큐가 128KiB 미만이고 드롭이 없는 상태가 45회 연속 관측되면 20%씩 높인다. 최대 28Mbps.
- 전송률 조절 시 H.264 인코더를 재시작하고 키프레임부터 전송을 재개한다. 오래된 시작 요청의 취소 오류는 새 인코더를 중지시키지 않는다.
- 마지막 세션 진단을 중지 이후에도 복사할 수 있다.
- Windows 진단에서 `adaptiveTargetMbps`, `adaptiveRestartCount`, `dataChannelBufferedBytes`, `dataChannelAdmittedFPS`를, iPad 진단에서 `recentCompletedFPS`를 같은 세션 ID로 비교한다.

이 변경은 전송 큐가 계속 꽉 차는 현상을 줄이려는 시도다. 데이터 채널 기반 H.264 전송은 RTP 영상의 혼잡 제어와 다르며, 실제 기기에서 1080p60 지속 여부를 검증해야 한다. 여러 명 시청은 아직 구현되지 않았다.
