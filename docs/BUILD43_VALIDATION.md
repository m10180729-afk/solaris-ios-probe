# Solaris 0.3.2 build43 검증 및 한계

## 진단에서 확인된 사실

- build42 Windows 송신자가 Intel Quick Sync H.264로 시작하고 프레임 데이터를 내보냈다.
- 기존 HTML 진단의 `fps`는 Windows에서 실제 디코딩/표시한 프레임 속도가 아니었다. `decodedFrames: 0`은 송신 역할에서 iPad 디코드를 측정할 수 없다는 뜻이므로 수신 실패의 근거로 사용하지 않는다.
- 송신 데이터 채널 대기열이 약 8MiB까지 커지고 드롭 카운터가 증가했다. 수신 손실/프레임 표시 여부를 확인할 iPad 측 진단도 없었다.
- 1080p120 시도에서는 NVENC/QSV/AMF/MF가 모두 첫 프레임을 내지 못했다. build43에서도 120fps 성공을 보장하지 않는다.

## build43 변경

- 영상 데이터 채널은 전송 대기 중인 바이트와 새 전체 프레임 크기의 합이 2MiB를 넘으면 해당 access unit 전체를 보내지 않는다. 부분 프레임은 보내지 않는다.
- H.264 GOP/IDR 간격을 약 1초로 줄여 비신뢰 데이터 채널의 패킷 손실 뒤 회복 대기를 줄인다.
- FFmpeg stdout access-unit 카운터에서 실제 네이티브 인코더 출력 FPS를 1초마다 계측한다. 별도로 데이터 채널에 투입한 FPS와 대기열 최고점/드롭 수를 노출한다.
- Windows 송신 진단의 `decodedFrames`는 송신 역할에서는 `null`이다. 이것은 iPad 디코드가 아니다.
- iPad의 **Windows→iPad 수신 진단 복사**는 완성 access unit 수, 수신 패킷, 미완성 프레임 폐기, 표시 레이어 enqueue/drop 수, 오류를 복사한다. 레이어 enqueue는 실제 화면 광출력/하드웨어 디코드 완료와 동일한 지표가 아니다.

## 아직 확인되지 않은 것

소스 테스트와 Windows/macOS CI 빌드는 기기 재생을 증명하지 않는다. iPad build43을 설치하고 Windows 하드웨어 1080p60으로 1분 이상 재생한 뒤 양쪽 진단을 함께 확인해야 한다. 그 테스트 전에 “60fps 안정” 또는 “해결”로 판정하지 않는다. 120fps는 60fps 양방향이 안정된 다음 별도 실험으로 취급한다.
