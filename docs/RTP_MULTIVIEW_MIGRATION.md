# Solaris P2P 화면 공유 전송 전환

목표: Windows, iPad에서 1080p60 영상과 화면 소리를 송신하고, 방의 여러 사용자가 시청한다. 서버는 신호 교환에만 쓰며 영상은 P2P로 전달한다. 한 화면을 시청자마다 따로 캡처하거나 인코딩하지 않는다.

## 현재 진단과 원인

- build46 세션 `4db144df-41eb-4d20-a200-8abeabcd34cc`의 Windows 송신은 연결 상태에서도 데이터 채널 큐가 2MiB까지 차고 265프레임을 버렸다. 목표 비트레이트 12→7→4Mbps 변경 때 인코더가 두 번 재시작되어 수초간 영상이 멈춘다.
- iPad→Windows는 WebRTC 영상 RTP 트랙이다. Windows→iPad의 `hardware60`은 FFmpeg H.264를 비신뢰 데이터 채널에 직접 분할해 보낸다. 이 둘은 같은 전송 경로가 아니다.
- `compatibility60`은 이미 표준 RTP 영상 트랙이지만, 기존 진단에서는 Windows WebView2가 OpenH264 소프트웨어 인코더를 사용해 캡처와 인코딩이 20fps 안팎이었다. 이 모드를 기본으로 바꾸는 것만으로 목표를 달성하지 못한다.
- Windows의 `availableOutgoingMbps`는 후보 쌍 추정치이며 실제 업로드 속도의 증거가 아니다. iPad 동일 세션의 수신 FPS 진단도 필요하다.

## 구현 경계

1. Windows 네이티브 송신에서 화면 캡처와 H.264 하드웨어 인코더를 한 번 실행한다. 선택한 GPU 인코더와 60fps 설정, SPS/PPS/IDR 간격을 실제 출력으로 확인한다.
2. 그 인코딩 결과를 Windows의 WebRTC **영상 RTP 트랙**으로 패킷화한다. 시청자마다 별도 `RTCPeerConnection`을 만들고 각각 SDP/ICE를 교환한다. 기존 iPad `RTCVideoTrack` 수신 뷰와 Windows `<video>` 수신기로 재생한다. 영상은 데이터 채널로 보내지 않는다.
3. 방의 각 시청자에게 `viewerID`를 부여한다. 현재 코드에는 이 식별자를 수신 진단 및 응답/ICE 신호에 담는 준비가 들어 있지만 송신부는 여전히 첫 번째 수신자 연결만 처리한다. 새 구현에서는 `sessionID`(방송 1회)와 `viewerID`(수신자 1명)를 모두 검증하고, 종료 시 해당 연결만 정리한다.
4. PLI/NACK·패킷 손실·수신 대역폭을 시청자별로 측정한다. 키프레임 요청을 인코더에 연결하고, 느린 수신자가 다른 시청자의 재생을 막지 않도록 시청자별 송신 큐를 분리한다. 시청자 N명에게 P2P 송출하면 업로드가 대략 N배 필요하다. 부족할 때 해상도나 프레임을 낮추는 동작을 명시한다.
5. 시스템 소리 Opus 트랙을 같은 시청자별 연결에 담고, 마이크는 제외한다.

## 출시 판정

- Windows 송신의 실제 인코딩 FPS, 시청자별 RTP `framesSent`, `bytesSent`, 큐 지연과 iPad의 `framesDecoded`, 수신 FPS, 패킷 손실을 동일한 세션과 `viewerID`로 대조한다.
- 움직임 많은 화면을 10분 이상 Windows→iPad, Windows→Windows, iPad→Windows에서 테스트한다. 중간에 재시작·장시간 정지·오디오 끊김 없이 1080p60 목표를 평가한다.
- 두 수신자 동시 시청, 한 명 입장/퇴장/재연결, 서로 다른 네트워크 및 대역폭 제한을 검증한다. 송신자 업로드가 부족하면 60fps를 보장할 수 없다.

build47은 큐 지연 및 인코더 재탐색을 줄이려는 시험용 수정본이며 이 조건을 만족하는 완성본이 아니다. 네이티브 WebRTC 영상 트랙과 시청자별 송신 연결을 Windows에서 컴파일하고 실기기로 검증하기 전에는 RTP/다인 시청 완성본이라고 표시하지 않는다.
