# Solaris build57 검증 기록 — 2026-10-11

이번 작업은 빌드56 통합 앱에서 신고된 화질/FPS 저하, Android 화면공유 종료, 서버/채널/탈퇴 UI 혼동을 수정한 체크포인트다. 실제 기기에서 문제가 해결됐다고 아직 단정하지 않는다.

## 확인한 원인과 변경

- 통합 UI의 기본 품질은 1080p/60fps/12Mbps였다. 빌드54의 Windows 네이티브 RTP 경로도 12/18Mbps였으므로 이 값 자체가 빌드54보다 낮았다고 단정할 수 없다. 빌드54의 별도 하드웨어 캡처 시작 경로는 25/60Mbps, iOS 최고화질 정책은 28/60Mbps였다.
- 새 통합 경로에는 다중 시청 수만으로 해상도/FPS를 낮추는 로직과, 시청자 중 가장 낮은 품질 요청을 공통 캡처 전체에 적용하는 로직이 있었다. iOS도 빌드54의 프레임·해상도 유지 정책 대신 balanced 정책을 적용하고 있었다. 이 경로들을 제거했다.
- 방송 품질 선택 UI를 삭제했다. 모든 플랫폼은 고화질/60fps를 요청하며 최대 목표는 가로 2560×1440 또는 그에 상응하는 세로/원본 비율이다. 작은 원본은 확대하지 않는다. Windows 시작/최대 예산은 25/60Mbps, iOS 기본 최소/최대는 빌드54의 28/60Mbps, Android는 기기 인코더 지원 크기/60fps와 고화질 RTP 파라미터를 사용한다. 연결이 나쁜 시청자의 비트레이트 요청은 공통 캡처 크기/FPS를 바꾸지 않는다.
- Windows 빌드54의 FFmpeg 하드웨어 인코더, RTP 패킷화, 타이밍/큐, 독립 시청자 복구는 재사용한다. iOS도 기존 ReplayKit 최신 프레임 펌프/H264 정책을 재사용한다. 방송 요청·계정·서버를 묶는 통합 신호/어댑터는 빌드55/56에 추가된 구조다. 전체 엔진을 완전히 동일하게 되돌렸다는 의미가 아니다.
- 정지 화면은 디코더 고장이나 네트워크 장애와 구별한다. 영상이 변하지 않았다는 이유만으로 품질을 낮추거나 연결을 반복해서 교체하지 않는다.
- Android는 H264 baseline 우선, 실제 화면 비율/인코더 크기 및 FPS 지원 확인, 협상 완료 후 인코더 설정, 첫 프레임 이후 방송 ready, 캡처 서비스 예외, 세션별 승인 요청, 안전한 정리, 기존 virtual display 회전/크기 변경, WebView 렌더러 복구를 구현했다. 기존 고정 1920×1080 가로 캡처와 시청자 요청에 따른 공통 source 변경을 제거했다.
- 정확한 Android 크래시 원인은 당시 Logcat/기종/OS 정보가 없어 확인하지 못했다. 이번 APK에서 재현 시 진단 내보내기는 네이티브 오류, 최근 Android 프로세스 종료 사유, 실제 캡처 크기와 제출 프레임 수를 포함한다. Java 예외 보강이 모든 네이티브 SIGSEGV를 해결했다고 주장하지 않는다.
- Discord 방식으로 서버 아이콘 열, 채널 목록, 중앙 방송/친구/파일 영역, 참여자 목록, 내 프로필/설정을 구분했다. 작은 프로필 접속 표시와 모바일 메뉴를 추가했다. 서버 탈퇴/삭제는 별도 서버 메뉴 아래 빨간 위험 영역으로 이동하고 확인 후 실행한다. 친구 삭제/차단도 별도 친구 메뉴로 이동했다.
- 계정 UID, RLS, 친구 관계, 파일 동의/청크/해시/복구는 유지했다. 새 DB 마이그레이션은 없다. 음성통화/마이크는 추가하지 않았다.

## 다음 실제 기기 시험

1. 두 기기를 모두 build57로 맞춘다. Android 공유 → 상대 시청 시작/종료/재입장, Windows/iPad 공유 → Android 시청을 각각 시험한다.
2. 방송 전 시청/방송 후 시청, 양방향 동시 공유, 정지 화면 1분, 회전, 시스템 캡처 중지, 취소 후 재시작을 확인한다.
3. 영상 품질 표시/진단에서 원본·수신 크기/FPS/비트레이트를 기록한다. 고화질 목표값과 실제 측정값을 구별한다.
4. Android가 다시 종료되면 앱 재실행 → 설정 → 진단 내보내기와 `adb logcat -b crash -d` 결과, 기종/Android 버전, 송신/수신 어느 쪽인지 기록한다. 토큰/개인정보는 삭제한다.
5. 화면공유와 파일 전송을 함께 실행하고 시청자 1→5명/다중 시청 시 영상 안정성과 발열을 확인한다. 실제 네트워크에서 이어받기도 별도 시험한다.
